# Vault Production Mode (`vault/`)

This document describes moving HashiCorp Vault out of dev-mode into a
persistent, TLS-secured setup, for the WAF/ModSecurity + Vault module
(secrets "encrypted and isolated").

## Overview

Vault previously ran as `vault server -dev`: everything (secrets, policies,
the AppRole setup) lived only in memory and was wiped on every container
restart. This didn't meet the subject's requirement of encrypted, isolated
secret storage, and was fragile — a crash mid-demo would lose all backend
credentials.

Vault now runs with:
- **Raft storage** — persistent, encrypted-at-rest, HashiCorp's current
  recommended backend (the older `file` backend is in maintenance mode).
- **Internal TLS** — the Vault API is served over HTTPS even for
  container-to-container traffic. The subject explicitly allows unencrypted
  internal traffic (Postgres, Redis do this), but Vault holds the most
  sensitive secrets in the system, so this is a deliberate
  defense-in-depth choice beyond the minimum requirement.
- **Automatic init + unseal** — handled by `vault-init.sh`, so the stack
  still comes up with a single `docker compose up -d`.

## Files

```
vault/
├── config/
│   ├── vault.hcl            # server config: raft storage, TLS listener
│   ├── backend-policy.hcl   # read-only ACL policy for the backend
│   └── vault-init.sh        # init / unseal / secrets / AppRole setup
└── certs/                   # generated by setup-certs.sh, not committed
    ├── vault.cert
    ├── vault.key
    └── ca.pem
```

See `vault.hcl`'s own documentation for the storage/listener config details,
and `backend-policy.hcl`'s for the ACL policy.

## TLS certificates

`setup-certs.sh` (already used for the Nginx certificate) was extended to
also generate one for `vault`, reusing the same local mkcert CA — so a
single `mkcert -install` covers both. The CA root is copied to
`vault/certs/ca.pem`, which every client (backend, `vault_init`) needs to
trust the self-signed certificate.

## Docker Compose changes

- `vault` service: `command` changed from `vault server -dev` to
  `vault server -config=/etc/vault/config/vault.hcl`; added
  `cap_add: [IPC_LOCK]` with `ulimits.memlock: -1` (mlock needs both the
  capability and an unlimited ulimit — the capability alone isn't enough);
  new `vault-data` volume for the raft storage.
- `vault_init` service: no longer takes a fixed `VAULT_TOKEN` — the script
  now reads the root token from its own init output instead.
- Two new one-shot `alpine` init containers (same pattern as the existing
  `prometheus-init`) `chown` the `vault-data` and `vault-keys` volumes to
  the `vault` user (UID 100) before the main containers start — Docker
  volumes default to `root` ownership, but the Vault process doesn't run as
  root.
- `backend` service: gained `VAULT_ADDR`/`VAULT_CACERT` (now `https://` and
  a CA path, not `http://`) and a read-only mount of `vault/certs`.

## `vault-init.sh` changes

The script now handles, in order, before the existing secrets/policy/AppRole
steps (unchanged from before):

1. **`vault operator init`** — runs only once. Guarded by checking whether
   `/vault/keys/init.json` (on the `vault-keys` volume) already exists, since
   Vault refuses to be initialized twice.
2. **`vault operator unseal`** — runs on every start where Vault reports
   `sealed: true` (i.e., every restart, since dev-mode's auto-unseal no
   longer applies). Uses 3 of the 5 generated Shamir key shares, read from
   the same `init.json`.
3. **Enabling the `secret/` KV v2 engine** — dev-mode auto-mounts this;
   production mode doesn't, so it has to be enabled explicitly
   (`vault secrets enable -path=secret -version=2 kv`), idempotently.

JSON parsing (root token, unseal keys) uses `grep`/`sed`/`cut` rather than
`jq` — `jq` isn't in the base image, and installing it at runtime via `apk
add` isn't reliable in this environment (network access from inside the
container can't be assumed).

## Known limitation

`vault_init` only runs once per container lifecycle — it performs the
unseal when *it* starts, not automatically every time the `vault` container
itself restarts independently. In this project, recovering from a `vault`
restart currently requires manually re-running `docker compose up -d
vault_init`. Documented here as a known limitation rather than solved, given
the project's scope — a "real" production setup would use an auto-unseal
mechanism (e.g. a cloud KMS) instead of Shamir shares requiring manual/
scripted intervention.

## Issues found and fixed while testing

Testing this end-to-end (rather than assuming the config was correct)
surfaced several real bugs:

1. **`vault.hcl` typos** — `adress` instead of `address`, and
   `disable_mock` instead of `disable_mlock`. Vault silently ignores unknown
   config fields (only logging a warning), so `disable_mlock` was never
   actually set — which is fatal on the Vault version in use, where it no
   longer has a default.
2. **Healthcheck deadlock** — `vault status` exits with code `2` whenever
   Vault is sealed or uninitialized, which Docker's healthcheck treats as
   failure. Since `vault_init` depends on `vault` being healthy, this created
   a deadlock: Vault could never become healthy without being unsealed, but
   unsealing needed `vault_init` to run, which needed Vault to be healthy.
   Fixed by changing the healthcheck to only treat exit code `1` (real
   connection/config error) as unhealthy.
3. **`mlock` failing under `cap_add: IPC_LOCK` alone** — Docker also
   enforces a `memlock` ulimit, defaulting to a low value regardless of
   granted capabilities. Fixed by adding `ulimits.memlock: {soft: -1, hard:
   -1}` alongside the existing capability.
4. **Volume permission errors** (`permission denied` on both
   `/vault/data` and `/vault/keys`) — Docker-created named volumes default
   to `root` ownership; the Vault process runs as UID 100. Fixed with
   dedicated one-shot `chown` init containers, same pattern as the existing
   `prometheus-init`.
5. **`jq: not found`** — the base image doesn't include `jq`, and installing
   it at container start via `apk add` failed silently in this environment.
   Rewrote the JSON parsing in `vault-init.sh` using only `grep`/`sed`/`cut`.
6. **Missing `secret/` mount** — `vault kv put` failed with a `403` on
   the CLI's preflight capability check, even using the root token. Root
   cause: dev-mode auto-mounts a KV v2 engine at `secret/`; production mode
   doesn't. Fixed by explicitly enabling it in `vault-init.sh`.
7. **Duplicate `VAULT_ADDR` in `.env`** — an old `http://0.0.0.0:8200` line
   was left in `.env` alongside the new `https://vault:8200` one. `.env`
   files silently use the *last* definition of a duplicated key, so Vault's
   own healthcheck kept using the stale HTTP value — producing a stream of
   `TLS handshake error: client sent an HTTP request to an HTTPS server`
   that looked like a client-code problem but was actually a config file
   duplicate.
8. **Backend's own Vault client** (`health.service.ts`, `checkVault()`) had
   `http://vault:8200` hardcoded and no CA configured on its HTTP client,
   so it kept failing to reach the now-HTTPS Vault, surfacing as `/health`
   returning `503`. Fixed by reading `VAULT_ADDR`/`VAULT_CACERT` from the
   environment and passing an `https.Agent` with the CA to the request —
   deliberately not using `VAULT_SKIP_VERIFY`/disabling verification, which
   would have defeated the purpose of adding TLS in the first place.

## How to test

1. `docker compose down && docker compose up -d` (a clean start exercises
   the full init/unseal path, not just a restart).
2. `docker compose exec vault vault status` — expect `Initialized: true`,
   `Sealed: false`, `Storage Type: raft`.
3. `docker compose logs vault_init` — expect to see secrets written, the
   policy loaded, AppRole enabled, and a RoleID/SecretID pair generated,
   with no errors.
4. `docker compose exec backend wget -qO- http://localhost:8000/health` —
   expect `{"status":"ok","database":"up","redis":"up","vault":"up"}`.
5. `docker compose ps` — `vault` and `backend` both `healthy`.
6. Restart resilience: `docker compose restart vault`, then
   `docker compose up -d vault_init` — confirm it detects the sealed state
   and unseals automatically without re-running `vault operator init`.
